# 既有 AI 教学课件参考价值分析

> 样本：历史工程教学课件  
> 分析目的：判断既有课件对 AgentSceneBuilder 产品设计、协议设计和 MVP 验收的参考价值。  
> 修正说明：旧课件中的共同界面与步骤形态只能作为 AI 的参考模式，不能直接成为产品的固定工作流。当前定位以 [`product-positioning-v2.md`](product-positioning-v2.md) 为准。

## 1. 结论

这批课件对 AgentSceneBuilder 具有**很高的经验管理与能力抽取价值**、**中等的实现参考价值**、**较低的直接代码复用价值**。

它们不是需要整体迁移的旧代码库，也不是未来产品的标准形态，而是一组已经完成真实交付的“任务案例”和“重复劳动证据”。应从中提取可描述的资产、能力、约束、失败经验与组合方法，交给 AI 在新任务中选择和重组。

| 参考维度 | 价值判断 | 说明 |
| --- | --- | --- |
| 产品定位 | 很高 | 样本集中在施工工艺、工程巡检、机电优化和仿真实训，与 V1 切口高度一致 |
| 场景协议 | 很高 | 多个项目重复出现步骤、镜头、场景状态、对象显隐、标注和动画 |
| 教学交互 | 很高 | 问答、评分、风险点、自动播放、步骤导航已经形成稳定模式 |
| 组件目录 | 高 | 建筑、管线、设备、施工机具、人员、标注等素材可反推首批组件需求 |
| Preview UX | 高 | 已形成左侧步骤、中间 3D、右侧讲解/数据、底部播放控制的共同布局 |
| 验证体系 | 高 | 现有空场景、资源加载、镜头和备份文件痕迹直接说明证据闭环的必要性 |
| 源码直接复用 | 低 | 单文件强耦合、项目定制代码多、缺乏统一数据层和测试 |
| 视觉资产复用 | 中 | GLB 可作为测试素材候选，但需先处理授权、命名、坐标、比例和质量 |

## 2. 样本概况

核心样本覆盖：

- 厂房环氧地坪漆施工；
- 地坪粘结强度试验；
- 大体积混凝土智能温控仿真实训；
- 教学楼施工场地巡检；
- 无机磨石施工工艺；
- 机电管线综合优化模拟；
- 水电工艺教学；
- 独立基础施工；
- 装配式保温外墙板施工；
- 一个 GLB/GLTF 模型编辑器。

项目同时包含 HTML 课件、Three.js 源码、GLB/RVT/SKP/PBIM 模型、教学脚本、表格、截图、演示视频、视频自动录制脚本和 Tauri 打包产物。这说明真实交付并非只有 3D 画面，而是一整条“脚本—课件—验证—视频—安装包”生产链。

## 3. 最重要的共同模式

### 3.1 既有课件常表现为教学状态机，但这不是唯一模型

现有 `Scene Document` 主要表达对象与步骤，但旧项目显示一个步骤通常同时包含：

- 教学标题、说明和完成状态；
- 相机位置与观察目标；
- 场景对象的可见性或参数状态；
- 自动播放时长与过渡；
- 问题、选项、正确答案和答题反馈；
- 当前步骤可用的操作；
- 风险点、监测值或评分变化。

因此，“场景状态 + 教学步骤”应被沉淀为一种可选能力或参考模式，不能成为所有场景的核心抽象。非线性探索、实时仿真、空间巡检和未来 AI 生成的新形态必须能够使用其他组织方式。

### 3.2 镜头是内容的一部分

多个项目为每一步保存独立的 camera/target，并使用 localStorage 保存人工校正后的视角。这说明镜头不是 Preview 的临时状态，而是教学内容资产。

产品影响：

- Scene Document 必须支持每步镜头引用或内联镜头覆盖；
- Preview 应提供“将当前视角写回步骤”的低成本操作；
- 验证应检查目标对象是否处于镜头可见范围；
- 需要区分作者镜头、用户自由观察和恢复教学镜头。

### 3.3 领域场景需要参数化状态，而不只是 transform

环氧地坪使用 `primer/mortar/putty/topcoat/clean` 等连续状态表达施工层进度；温控仿真使用温度、时间、流量、风险等级；巡检使用风险点发现与整改状态。

产品影响：

- 不宜把所有变化都硬塞进 position/rotation/visibility；
- step 需要通用 `state` 或 `bindings`；
- 组件需要公开可验证的参数和状态；
- 对连续数值应支持插值，对离散状态应支持切换。

### 3.4 GLB 导入是刚需，不是未来增强

多数工程课件依赖现有 GLB 资产。只支持 box、plane 等程序几何体可以完成技术样例，但无法覆盖真实课件生产。

V1 应至少支持：

- GLB/GLTF 资源对象；
- transform、显隐、材质覆盖和包围盒检查；
- 加载失败、空模型、极端比例和离开镜头范围检测；
- 导出时复制资源并重写稳定相对路径。

不需要在 V1 内解决 RVT/SKP/PBIM 转换，但应把这些格式记录为导入前处理链的输入来源。

### 3.5 预览界面已经形成稳定骨架

代表性界面反复采用：

```text
顶部：项目标题、视图与工具
左侧：章节/工序/实训流程
中央：Three.js 场景
右侧：步骤讲解、问答、数据或评价
底部：上一步、播放、重置、下一步、时间轴
```

这套结构可以沉淀为一个可复用的 Teaching Player 能力与案例，但不应成为默认且唯一的产品壳层。AI 应能根据任务选择它、修改它，或组合出完全不同的信息架构。

### 3.6 问答和评价是高频需求

现有课件广泛包含步骤问题、选项、正确答案、成功反馈、风险点计数和最终评分。它们不是纯 3D 能力，但决定课件是否真正具备教学价值。

建议拆分为可选的 `teaching` 扩展协议，而不是塞入 Three renderer：

```json
{
  "teaching": {
    "questions": [],
    "completion": {},
    "assessment": {},
    "feedback": {}
  }
}
```

MVP 可先渲染单选题和即时反馈，复杂评分规则放在后续版本。

### 3.7 交付链不仅是 HTML

旧项目出现 Tauri 安装包、使用说明、MP4 演示视频、旁白、字幕、截图和自动录屏脚本。正式产品应把 HTML 作为核心产物，但保留派生输出的架构位置。

推荐层次：

1. V1：静态 HTML 目录包、截图、manifest；
2. V1.x：自动播放/录屏友好模式；
3. 后续：视频导出适配器、桌面包装适配器、交付文档模板。

## 4. 现有实现暴露的问题

### 4.1 单文件强耦合

代表性 `app.js` 约 1,300–6,500 行，最大超过 200 KB。教学内容、Three.js 场景、DOM、动画、模型加载、答题和状态管理混在一起。AI 后续修改容易产生局部修复、重复代码和意外回归。

这直接验证了 Scene Document、Command API、Renderer 和 Teaching Player 分层的必要性。

### 4.2 项目之间复制框架代码

几乎每个项目都重新实现步骤列表、上一步/下一步、自动播放、镜头切换、resize、OrbitControls 和状态过渡。AgentSceneBuilder 应把这些变成运行时能力，项目只保存内容和必要扩展。

### 4.3 内容与实现不可独立续改

修改一个步骤的文案、镜头或对象状态通常需要直接编辑 `app.js`。没有统一 schema，也不能在不理解整个文件的情况下安全修改。

### 4.4 资产管理缺乏规范

存在中文名、数字后缀、重复模型、`未命名.glb`、备份目录和多个版本并存。说明产品需要 asset ID、原始文件名、内容哈希、来源、尺寸和坐标修正信息，而不能只保存一个路径字符串。

### 4.5 验证依赖人工和临时脚本

项目中已有 verification screenshot、preview-final、smoke-test、contact sheet、录屏脚本和日志，这证明团队一直在做验证，只是验证没有成为统一产品能力。

其中巡检课件的预览截图出现主体模型几乎不可见的情况，是典型的“页面成功打开，但课件结果不可用”。这正适合作为视觉证据测试样本。

### 4.6 版本痕迹说明修改风险高

存在 `app.js.backup`、`app_fixed.js`、`.broken-*`、`.tmp` 和重复交互动画目录。这类痕迹说明当前方式缺少原子修改、revision、迁移和回滚边界。

## 5. 对 V1 设计的具体修正

结合这些真实样本，应优先建设能力管理和经验复用机制，而不是固化既有课件形态。

### P0：作为可复用底层能力纳入 MVP

1. GLB/GLTF 资源对象与可靠的资源路径处理；
2. Step 除 show/hide/highlight 外，增加 duration、transition、state bindings；
3. 教学镜头保存、恢复和“写回当前步骤”；
4. 可被不同上层形态复用的时间、状态与行为能力；
5. Teaching Player 作为首个参考组合，而非默认壳层；
6. 资源加载、包围盒、镜头可见性、空画面和 console error 证据；
7. 静态目录包导出，保证 GLB 等资源离线可加载。

### P1：协议预留，首版做最小实现

1. 单选题、即时反馈和步骤完成条件；
2. hotspot/risk point 点击交互；
3. 数值参数、图表数据和组件状态绑定；
4. 学习进度和简单评分；
5. 面向自动录屏的确定性播放模式。

### P2：后续适配

1. Tauri/桌面安装包；
2. 视频、旁白和字幕自动生产；
3. 复杂仿真模型和规则引擎；
4. 教师端、学生端和报告系统；
5. RVT/SKP/PBIM 转换流水线。

## 6. 可直接作为验收样本的旧项目

| 样本 | 适合验证的能力 |
| --- | --- |
| 厂房环氧地坪漆施工 | 多步骤、层状态插值、问答、工具模型、自动播放 |
| 教学楼施工场地巡检 | GLB 组合、风险热点、镜头可见性、整改状态 |
| 机电管线综合优化 | 调整前/后对比、管线组件、颜色语义、复杂场景 |
| 装配式保温外墙板 | 吊装流程、多人/设备/构件协同、多段动画 |
| 大体积混凝土温控 | 参数化仿真、热力表达、图表、预警和评价扩展 |
| 独立基础施工 | 程序几何、多工序状态、确定性视频录制 |

建议不要一次迁移全部项目。先选择三个金丝雀样本：

1. **厂房环氧地坪**：验证标准教学流程；
2. **教学楼巡检**：验证模型导入、热点和视觉证据；
3. **大体积混凝土温控**：验证扩展机制是否能承载参数化实训，而不污染 core。

## 7. 对产品定位的最终判断

旧项目没有要求 AgentSceneBuilder 复制一种课件形态，而是证明了管理可复用经验和能力的价值。真实定位更接近：

> 面向 AI Agent 的可发现、可组合、可验证、可演化的 3D 场景能力与经验基座。

核心不是统一最终作品，而是让 AI 复用资产、能力、约束、证据和历史经验，在不同任务中形成新的合理组合。

## 8. 建议的下一步

在设计 `Scene Document 0.1` 前，应先从多个旧项目中反向抽取资产、能力、约束和案例，而不是只抽取步骤。然后用至少两个不同组织形态的新任务验证：相同底层能力能否被 AI 重组，而无需修改 core。

该过程不要求旧项目直接运行在新框架中，目标是用真实经验压测能力发现、组合与证据协议，避免把任何一个历史项目的实现方式升级为产品标准。
