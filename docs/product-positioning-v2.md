# AgentSceneBuilder 定位与实现方法 V2

> 状态：历史定位记录。现行定位见 [V3](product-positioning-v3.md)。
>
> 说明：本文修正此前把既有课件形态过度固化为产品标准的问题。旧课件是经验来源，不是目标产品模板。

## 1. 核心判断

AgentSceneBuilder 的核心不是规定 AI 应该如何制作课件，也不是提供一套固定的步骤播放器、编辑器布局或教学模板。

它真正要解决的问题是：

> AI 每次构建 3D 场景时，都在重复发现资产、理解坐标、编写基础代码、处理加载、组织交互、调试镜头和验证结果；已有项目中的有效经验又无法被下一次任务直接理解和组合。

因此，AgentSceneBuilder 应定位为：

> **面向 AI Agent 的可发现、可组合、可验证、可演化的 3D 场景能力与经验基座。**

它把过去项目中具有复用价值的事实和能力转化为 AI 可理解的资源，让 AI 根据新的目标选择、组合、修改或舍弃，而不是把过去面向人类的交互形式变成唯一标准。

## 2. 产品价值

产品不替 AI 决定最终形式。产品应帮助 AI：

1. 知道当前有哪些可用资产、能力、行为和历史案例；
2. 理解每项资源适合什么、不适合什么、需要哪些前提；
3. 以低成本组合和调整这些资源；
4. 看到组合后的结构、运行和视觉结果；
5. 保存本次成功或失败经验，供以后检索和改进；
6. 在现有能力不够时，安全地创建新实现，而不是被模板阻塞。

减少重复工作的方式不是强制所有项目走同一流程，而是让 AI 不必重复解决已经解决过的底层问题。

## 3. 什么应该稳定，什么必须开放

### 3.1 应该稳定的最小内核

稳定的是管理方式和互操作边界，而不是具体课件形态：

- 资源如何被描述、定位、版本化和追踪来源；
- 能力如何声明输入、输出、约束、副作用和运行要求；
- 场景实体如何获得稳定身份并建立关系；
- 修改如何被执行、记录、验证和回滚；
- 证据如何与一次执行、一个产物和一个资源版本关联；
- 扩展如何注册和被 AI 发现；
- 成功案例与失败经验如何保存为可检索参考。

### 3.2 不应固化的内容

- 课件必须由若干线性步骤组成；
- 页面必须采用左侧步骤、中央 3D、右侧说明的布局；
- 教学一定包含选择题、评分或自动播放；
- 场景必须由某个固定行业模板开始；
- 动画只能使用预定义的少量类型；
- Three.js 是唯一渲染或交付方式；
- 过去成功的实现自动成为未来任务的最佳实践。

这些内容可以作为候选模式存在，但必须附带适用条件，并允许 AI 忽略、改写或组合。

## 4. 产品的核心管理对象

AgentSceneBuilder 不以“模板”为中心，而以六类可组合资源为中心。

### 4.1 Asset：资产

模型、纹理、图片、字体、音频、视频、文档以及程序化几何资源。

AI 需要知道的不只是文件路径，还包括：

- 语义名称、标签和用途；
- 格式、尺寸、坐标系、单位和包围盒；
- 来源、授权、版本和内容哈希；
- 预览图与质量信息；
- 已知问题和使用示例；
- 可执行的规范化或转换操作。

### 4.2 Capability：能力

一个可以被 AI 调用的原子或复合操作，例如加载 GLB、创建标注、对齐对象、计算包围盒、生成管线、设置镜头、检查可见性或导出网页。

每项能力需要自描述：

- 它解决什么问题；
- 输入和输出；
- 前置条件与约束；
- 是否修改状态；
- 失败模式；
- 可返回的证据；
- 示例和历史成功率；
- 所属实现与版本。

### 4.3 Entity / Relation：实体与关系

Scene Document 保存当前任务的场景事实，但不应尝试预先定义所有领域语义。

最小事实包括：

- 稳定 ID；
- 类型或能力声明；
- 属性和 transform；
- 资源引用；
- 父子、目标、依赖、约束等关系；
- 可扩展的领域数据。

步骤、问答、风险点、测温数据或施工状态都可以通过扩展实体与关系表达，而不是全部进入核心 schema。

### 4.4 Behavior：行为

行为描述对象或系统如何随事件和时间变化，例如移动、显隐、参数变化、碰撞响应、状态切换、仿真更新。

行为既可以是声明式配置，也可以引用受控代码模块。系统管理其接口、权限和证据，但不限制未来只能使用当前已有的动画类型。

### 4.5 Pattern / Case：模式与案例

旧课件中反复出现的步骤导航、教学镜头、风险巡检、前后对比等，应保存为“参考模式”或“案例”，而不是核心规则。

案例需要包含：

- 当时的目标和上下文；
- 使用了哪些资产与能力；
- 关键设计决策；
- 最终产物与证据；
- 已知缺陷；
- 哪些部分可能适用于其他任务。

AI 检索案例后进行推理和重组，而不是实例化一个不可变模板。

### 4.6 Evidence：证据

证据是系统判断和持续演化的基础，包括结构事实、运行日志、截图、性能、人工反馈和任务结果。

证据不仅用于验收，也用于回答：某个能力是否可靠、某种组合在什么场景有效、过去失败的原因是什么。

## 5. AI 的工作方式

```text
理解任务目标与约束
       ↓
检索相关资产、能力、模式和案例
       ↓
形成当前任务的组合方案
       ↓
调用能力创建或修改场景
       ↓
运行并获取证据
       ↓
保留、替换、重组或创建新能力
       ↓
交付产物，并沉淀本次案例
```

其中只有资源管理、能力调用、状态记录和证据链是系统强约束；“组合方案”属于 AI 的决策空间。

## 6. 对既有课件的正确使用方式

旧项目不应被总结为一套统一播放器，而应被拆解为可供 AI 参考的资源图谱。

例如“厂房环氧地坪施工”可以贡献：

- 环氧施工领域术语和对象；
- 地坪分层表达方法；
- 施工工具 GLB 资产；
- 分层状态渐变的实现能力；
- 某些镜头和问答组织案例；
- 资产加载、视角和维护方面的失败经验。

未来 AI 可以只使用其中的地坪分层能力，配合完全不同的界面、叙事结构和交互方式。它不需要复制原课件。

## 7. 实现架构

```text
AI Agent / Human Tool
          │
          ▼
Discovery & Context API
  检索资产、能力、案例、约束和证据
          │
          ▼
Composition Workspace
  当前任务的 Scene Document、计划与变更记录
          │
          ▼
Capability Runtime
  执行内置能力、插件能力和受控自定义实现
          │
          ▼
Renderer / Simulator / Exporter Adapters
          │
          ▼
Evidence & Experience Store
  结构、日志、截图、评价、案例和失败记录
```

### 7.1 Core

Core 只负责：

- 资源标识与引用；
- 场景实体、关系和扩展数据；
- 变更集、revision、原子写入和历史；
- 能力注册、发现与调用契约；
- 证据 envelope 和 provenance；
- schema/extension 版本管理。

Core 不包含教学流程、页面布局和具体行业判断。

### 7.2 Catalog

Catalog 不是组件模板列表，而是 AI 可查询的能力目录。它同时登记资产、组件、行为、验证器、导出器、案例和领域知识。

目录查询至少支持：

- 按目标、标签和输入类型检索；
- 查看适用条件、限制和示例；
- 查看依赖和兼容版本；
- 查看真实运行证据与已知失败；
- 比较多个候选能力。

### 7.3 Capability Runtime

运行时支持三个层级：

1. 内置可信能力：稳定、测试充分；
2. 已注册插件能力：具有 manifest、版本和权限边界；
3. 任务级临时代码：允许 AI 探索，但在隔离环境运行，不能自动升级为可信能力。

成功的临时代码可以在评审后沉淀为新能力。这样既保留 AI 演化空间，又避免未经验证的实现污染内核。

### 7.4 Adapters

Three.js 是第一渲染适配器。Teaching Player、编辑器、仿真面板、视频输出和桌面包装都是可组合的输出或交互适配器，不构成产品核心。

## 8. Scene Document 的重新定位

Scene Document 不是完整产品协议，也不是未来所有教学形式的统一 schema。它只是某次任务当前场景状态的可交换表示。

建议采用“稳定核心 + 声明能力 + 命名扩展”的结构：

```json
{
  "specVersion": "0.1",
  "revision": 12,
  "metadata": {},
  "entities": [],
  "relations": [],
  "resources": [],
  "behaviors": [],
  "uses": [
    { "capability": "three.render", "version": "^0.1" },
    { "capability": "teaching.sequence", "version": "^0.1" }
  ],
  "extensions": {}
}
```

如果任务不需要教学步骤，就不声明 `teaching.sequence`；如果未来出现空间探索、分支叙事或实时仿真，可以声明其他能力而无需修改 core。

## 9. Command API 的重新定位

不应把 `add_step`、`add_label` 等当前功能清单永久固化为唯一操作集合。

API 分为两层：

### 9.1 稳定的通用操作

- discover：发现资源和能力；
- inspect：读取事实、接口和证据；
- apply_changeset：原子应用实体/关系变更；
- invoke：调用已注册能力；
- validate：按声明的能力和扩展执行验证；
- render/export：调用相应适配器；
- record_case：沉淀任务结果和经验。

### 9.2 可演化的能力操作

`teaching.add_step`、`annotation.create_label`、`construction.create_scaffold` 等通过 capability manifest 暴露。AI 在运行时发现其参数，而不是要求 core 永久理解所有操作。

## 10. 首个 MVP

MVP 不以完成某种固定课件为唯一验收，而以证明“AI 能复用经验并减少重复工作”为目标。

### 10.1 MVP 能力

- 建立资产索引，能读取 GLB 元数据、预览和已知问题；
- 建立 capability manifest 与发现接口；
- 提供通用 Scene Document 与原子变更集；
- 提供 Three.js 基础渲染、GLB 加载、镜头和截图能力；
- 将旧课件拆出少量参考模式与案例；
- 返回带来源和 revision 的证据；
- 允许任务级自定义行为，不要求先修改 core；
- 能把一次成功组合保存为新案例。

### 10.2 MVP 验收实验

选择两个结构不同的任务，而不是复刻同一个播放器：

1. 从旧课件资产和能力中组合一个施工过程说明；
2. 使用相同底层能力组合一个非线性的工程巡检体验。

验收重点：

- 两个任务是否复用了资产加载、镜头、标注、状态和验证能力；
- 是否能采用不同的信息结构和交互形式；
- AI 是否能从目录中选择能力，而不是依赖硬编码提示；
- 新需求是否能通过扩展实现而无需修改 core；
- 相比从零写 Three.js，重复代码和重复调试是否显著减少。

## 11. 设计原则

1. **固化接口，不固化答案。**
2. **管理可复用能力，不规定最终作品形态。**
3. **案例提供上下文，不拥有强制权。**
4. **允许 AI 创建新组合和新能力，但必须保留权限与证据边界。**
5. **任何抽象只有被多个真实任务验证后，才有资格进入稳定内核。**
6. **对历史实现同时保存成功经验和失败限制。**
7. **产品是否成功，以减少 AI 的重复劳动和提高结果可靠性衡量。**

## 12. 当前正式设计顺序

1. 定义资源与 capability manifest；
2. 定义最小 Scene Entity / Relation / Changeset；
3. 定义 evidence 与 provenance；
4. 从旧项目建立首批资产、能力和案例索引；
5. 用两个不同形态的任务验证组合自由度；
6. 验证后再决定哪些领域扩展值得标准化。

原计划优先冻结完整教学 step schema 和 Preview UX，应暂缓。它们应先作为可选扩展和参考案例接受多任务验证。
