> 状态：产品基线草案  
> 阶段：从概念设计进入 MVP 详细设计  
> 本文用于统一产品、交互、协议和工程实现的决策。

> 注意：本文保留为阶段性设计记录，其中将教学步骤和 Preview 形态作为 V1 主骨架的判断已不再作为当前基线。当前定位以 [`product-positioning-v3.md`](product-positioning-v3.md) 为准；文中早期 MCP 接入设想已移出当前路线。

## 1. 产品定义

### 1.1 一句话定位

AgentSceneBuilder 是面向 AI Agent 的可验证 3D 场景生产工具：AI 通过结构化命令创建和修改场景，系统负责渲染、检查并返回证据，最终导出可交付的交互网页。

### 1.2 产品类别

它不是传统 3D 编辑器，也不是文生 3D 模型服务。它位于 AI Agent 与 Three.js 之间，是一层“场景协议 + 执行运行时 + 验证闭环”。

```text
用户意图
  -> AI Agent 规划
  -> AgentSceneBuilder 结构化执行
  -> Scene Document 持久化
  -> Three.js 预览与导出
  -> 结构/运行/视觉证据
  -> AI 修正或用户验收
```

### 1.3 首个切入市场

V1 聚焦“工程教学与流程演示”，尤其是需要在网页中讲清对象、空间关系和操作步骤的场景，例如：

- 建筑施工工序演示；
- 机电设备结构与工作原理讲解；
- 安全培训与操作流程课件；
- 面向客户的轻量工程方案说明。

选择该切口的原因：它需要 3D 表达，但通常不要求 BIM 级精度；步骤、标注、镜头和高亮比复杂建模更重要；HTML 交付天然适合培训、课件和分享。

## 2. 目标用户与任务

### 2.1 核心用户

**首要用户：使用编码 Agent 的技术型内容生产者**

他们能描述目标、准备参考资料并检查结果，但不希望手写和维护大量 Three.js 代码。典型角色包括工程数字化开发者、技术培训课件制作者、解决方案工程师。

**次要用户：Agent 平台与工具开发者**

他们通过 Skill、CLI 或宿主插件把 3D 场景能力接入自己的 Agent 工作流，关心协议稳定性、可观测性和失败恢复。

**结果验收者：教师、工程师和项目负责人**

他们主要查看预览、逐步播放、提出修改并接收导出结果，不是 V1 的主要建模操作者。

### 2.2 核心 Job to Be Done

> 当我需要讲解一个具有空间关系和操作顺序的工程主题时，我希望把自然语言目标和少量参考信息快速变成可交互、可修改、可验证的 3D 网页演示，从而减少手工建模和前端开发成本。

### 2.3 用户当前替代方案

| 方案 | 优点 | 主要缺口 |
| --- | --- | --- |
| 手写 Three.js | 灵活、网页原生 | 生成后难维护，AI 修改易破坏整体，验证弱 |
| Blender/Revit 后导出 | 专业能力强 | 工具重、自动化链长、网页交互需二次开发 |
| 视频/二维课件 | 制作和播放简单 | 空间关系表达弱，不能自由观察和交互 |
| 固定 3D 模板 | 上手快 | 很快受模板边界限制，难持续扩展 |

## 3. 核心价值主张

V1 必须同时成立的三项价值：

1. **Agent 可操作**：常见建场景动作可通过稳定、细粒度、可组合的结构化命令完成。
2. **结果可续改**：Scene Document 是独立于生成代码的事实来源，任何一次任务都能在原场景上继续。
3. **产物可验证**：每次关键操作都能返回结构、运行和视觉证据，而不是只返回“执行成功”。

产品的差异化不在于生成更复杂的模型，而在于更可靠地完成“生成—观察—修正—交付”闭环。

## 4. V1 产品闭环

### 4.1 标准任务流

1. 用户向 Agent 描述演示目标、受众和关键步骤。
2. Agent 创建 Scene Document，设置单位、标题和领域。
3. Agent 添加基础对象或领域组件，并添加材质、镜头、标注和步骤。
4. 系统在命令执行时做快速结构检查，返回变更摘要。
5. Agent 主动执行完整验证并渲染关键步骤预览。
6. 系统返回截图、场景摘要、警告和运行错误。
7. Agent 根据证据修正场景；用户可在预览页验收。
8. 系统导出可离线打开或部署的 HTML 产物及 manifest。

### 4.2 最小可演示用例

V1 用“二层建筑外墙保温板施工演示”作为贯穿式基准场景。完整验收任务应包含：

- 一个可识别的建筑主体；
- 一块从初始位置移动到墙面的保温板；
- 至少两个教学步骤；
- 每步有指定镜头、说明和高亮对象；
- 至少一个与目标对象保持关联的标注；
- 可生成关键步骤截图；
- 可导出无需开发服务器即可查看的 HTML 演示。

## 5. V1 范围

### 5.1 必须具备

**场景数据**

- Scene Document 的读取、写入、版本识别与 schema 校验；
- 基础对象：box、plane、cylinder、line、label、arrow；
- 材质、透视相机、对象分组；
- step 的显隐、高亮、镜头切换和 move 动画；
- 稳定 ID 与对象引用。

**Agent 操作**

- create、inspect、add、update、remove；
- set_camera、add_step；
- validate、render、export_html；
- 每条修改命令返回 changed、warnings 和 scene revision。

**预览与证据**

- 本地预览页，支持轨道视角、步骤前后切换和重新播放；
- 场景树与当前步骤信息；
- 结构验证报告、浏览器控制台错误、关键步骤截图；
- 空白画面和资源缺失检测；
- 导出 manifest，记录源场景版本、时间和入口文件。

**交付**

- CLI 为首个完整入口；
- 静态 HTML 导出；
- Windows/macOS/Linux 下的 Node.js 本地工作流。

### 5.2 V1 明确不做

- 通用网格建模、雕刻、骨骼动画和专业材质编辑；
- BIM/IFC 语义完整性和工程算量；
- 多人实时协作、云端项目管理和账号系统；
- 自然语言理解层或内置大模型编排；
- 完整桌面级可视化编辑器；
- 移动端编辑；
- 面向所有行业的庞大组件市场。

## 6. 产品形态与信息架构

### 6.1 CLI（主入口）

```text
agentscene create <scene>
agentscene inspect <scene> [--json]
agentscene apply <scene> --command <file|json>
agentscene validate <scene> [--strict]
agentscene preview <scene> [--step <id>]
agentscene render <scene> --out <png>
agentscene export-html <scene> --out <dir>
```

CLI 的 stdout 在 `--json` 模式下必须只输出机器可解析结果；日志写入 stderr。失败必须返回非零退出码和稳定错误码。

### 6.2 Preview（人类验收入口）

```text
┌──────────────────────────────────────────────────────────┐
│ 项目标题        验证状态       重新加载        导出 HTML │
├──────────────┬───────────────────────────────┬───────────┤
│ 场景树       │                               │ 属性/证据 │
│ 对象         │          3D 画布              │ 当前对象  │
│ 相机         │                               │ 警告      │
│ 步骤         │                               │ 运行信息  │
├──────────────┴───────────────────────────────┴───────────┤
│ 上一步   2/4 当前步骤标题   播放/暂停   下一步           │
└──────────────────────────────────────────────────────────┘
```

V1 的 Preview 以“查看和验收”为主，只允许有限微调（相机取景、对象 transform），不承担复杂创作。

### 6.3 适配器

CLI 打通并稳定后，再提供宿主插件封装和静态 Web/HTTP 预览。适配器只能调用 core，不复制校验、命令执行或证据逻辑。

## 7. 关键交互规则

### 7.1 命令必须可解释

每次修改返回：命令 ID、执行结果、场景 revision、变更对象、自动修正、警告、下一步建议检查项。禁止只返回布尔值。

### 7.2 修改必须避免静默覆盖

- update/remove 必须指定对象 ID；
- 可选传入 `expected_revision` 实现乐观并发控制；
- 删除被引用对象时默认失败，显式 `cascade: true` 才级联处理；
- 命令失败时不写入半成品场景。

### 7.3 验证分层

- `error`：无法可靠渲染或引用已损坏，命令/导出失败；
- `warning`：可以渲染，但教学表达或兼容性可能有问题；
- `info`：优化建议，不影响完成。

结构验证不能替代视觉验收；截图失败也不能抹去已获得的结构证据。

### 7.4 坐标约定

V1 固定使用右手坐标系、Y 轴向上、米为推荐单位、角度在文档中使用弧度。所有入口展示同一约定，避免 Agent 猜测。

## 8. 成功指标

### 8.1 MVP 验收指标

- 基准场景能完全通过 CLI 从空文件构建，不需手改 Three.js；
- 同一 Scene Document 连续执行 50 条有效命令后仍可读取、验证和渲染；
- 所有失败命令均不破坏原文件；
- 基准场景每个步骤均能生成非空截图且无 console error；
- 导出的 HTML 在断开开发服务器后仍可打开并完成步骤切换；
- Agent 仅依据 `inspect + validate + render evidence` 能定位并修正至少三类预设错误：缺失引用、不可见对象、错误镜头。

### 8.2 产品有效性指标（试用阶段）

- 首个可验收场景的中位制作时间；
- 首次导出成功率；
- 每个任务从初稿到验收的修正轮数；
- 命令成功率与失败原因分布；
- 导出后仍需人工修改源代码的任务比例。

北极星指标暂定为：**每周成功导出且通过验证的演示场景数**。

## 9. 设计原则

1. 协议优先于界面，场景事实优先于渲染实现。
2. 先覆盖完整闭环，再扩展对象和行业组件数量。
3. 默认行为应可预测；隐式推断必须体现在证据中。
4. 对 Agent 返回结构化事实，对人返回可快速判断的预览。
5. 核心能力本地可用，网络服务只能作为可选增强。
6. 领域组件可以加速创作，但必须能展开为可检查的基础对象。

## 10. 版本实施顺序

### Milestone A：可修改的场景事实

- 收紧并版本化 Scene Schema；
- 实现 core 的 load/save/validate；
- 实现原子化 command apply 与 revision；
- 用基准场景建立协议测试。

完成定义：不依赖渲染器，也能可靠创建、修改、检查场景。

### Milestone B：可观察的 Three.js 场景

- 基础对象与材质渲染；
- 相机、标签、高亮和步骤；
- 本地 Preview 与静态 HTML 导出。

完成定义：人可以在浏览器中顺畅查看完整基准演示。

### Milestone C：可验证的 Agent 闭环

- 无头浏览器截图与 console 捕获；
- 结构、运行和视觉证据统一返回；
- CLI 机器输出、稳定错误码和端到端测试。

完成定义：Agent 可以依据证据自行发现并修正预设错误。

### Milestone D：接入与领域增强

- Skill/CLI 插件封装与静态 Web 预览；
- 首批施工教学组件；
- Preview 的有限人工微调。

## 11. 当前需要冻结的产品决策

开始 Milestone A 前，应将以下内容作为首轮详细设计评审项：

1. Scene Document 0.1 的严格字段、默认值与迁移策略；
2. Command Envelope、错误码、revision 和原子写入语义；
3. component 展开后是持久化结果还是渲染时派生结果；
4. label 使用 3D 对象、CSS2D 还是导出兼容层；
5. HTML 导出的离线边界（单文件或目录包）；
6. 截图的一致性要求与无头浏览器运行基线。

## 12. 下一份设计产物

产品基线确认后，正式设计应按以下顺序继续：

1. `scene-document-v0.1.md`：字段语义、约束、兼容与迁移；
2. `command-protocol-v0.1.md`：命令、响应、错误与事务语义；
3. `preview-ux-v0.1.md`：预览页状态、交互与异常态；
4. `mvp-acceptance-tests.md`：从用户任务出发的端到端验收用例。
